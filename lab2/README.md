# Лабораторная работа №2

## Описание

В лабораторной исследуются следующие типы коллекций:

- **List** - динамический массив
- **LinkedList** - двусвязный список
- **Queue** - очередь (FIFO)
- **Stack** - стек (LIFO)
- **ImmutableList** - неизменяемый список

Для каждой коллекции измеряется время выполнения следующих операций:

**Добавление элементов:**
- В конец коллекции
- В начало коллекции
- В середину коллекции

**Удаление элементов:**
- Из начала коллекции
- Из конца коллекции
- Из середины коллекции

**Дополнительные операции:**
- Поиск элемента по значению
- Получение элемента по индексу (если применимо)

## Используемые технологии и библиотеки

- **.NET 8.0** - платформа для разработки
- **C#** - язык программирования
- **xUnit** - фреймворк для написания автоматизированных тестов
- **System.Diagnostics.Stopwatch** - для измерения времени выполнения операций
- **System.Collections.Immutable** - библиотека для работы с ImmutableList

## Инструкция по запуску

### Требования

- Установленный .NET SDK версии 8.0 или выше
- Терминал или командная строка

### Шаги для запуска

1. Откройте терминал в папке проекта `Gunba/lab2`

2. Восстановите зависимости (если нужно):
   ```bash
   dotnet restore
   ```

3. Запустите основное приложение для анализа производительности:
   ```bash
   dotnet run
   ```
   
   Приложение выполнит замеры производительности для всех коллекций и выведет результаты в консоль. Результаты также автоматически сохраняются в файл `performance_results.txt`.

4. Запустите автоматизированные тесты для проверки корректности операций:
   ```bash
   dotnet test
   ```
   
   Или для более подробного вывода:
   ```bash
   dotnet test --verbosity normal
   ```

### Параметры тестирования

В файле `CollectionPerformanceMeasurer.cs` можно изменить следующие параметры:

- `CollectionSize` - размер коллекции для тестирования (по умолчанию 100 000 элементов)
- `MeasurementIterations` - количество итераций для усреднения результатов (по умолчанию 5)
- `WarmupIterations` - количество итераций прогрева перед измерениями (по умолчанию 3)

## Подход к реализации замеров

### Архитектура решения

1. **Базовый класс `CollectionPerformanceMeasurer`**:
   - Абстрактные методы для каждой операции
   - Унифицированный метод `MeasureOperation` для измерения времени
   - Метод `MeasureAll` для выполнения всех измерений

2. **Специализированные классы**:
   - Каждая коллекция имеет свой класс-измеритель
   - Реализация специфичных для коллекции операций
   - Обработка ограничений коллекций (например, Queue не поддерживает прямой доступ по индексу)

### Методология измерений

1. **Инициализация коллекций** - создается пустая коллекция нужного типа
2. **Заполнение данными** - коллекция заполняется заданным количеством элементов (100 000)
3. **Прогрев (Warmup)** - выполняется 3 итерации операции для стабилизации JIT-компиляции и кэша
4. **Измерение времени** - для каждой операции используется `Stopwatch` для точного измерения времени
5. **Многократное выполнение** - каждая операция выполняется 5 раз
6. **Усреднение результатов** - вычисляется среднее время выполнения для каждой операции
7. **Вывод результатов** - результаты выводятся в консоль и сохраняются в файл

### Особенности реализации

- **List<T>**: Использует предварительное выделение `Capacity` для оптимизации
- **LinkedList<T>**: Для доступа к середине используется последовательный обход узлов
- **Queue<T>**: Операции, не поддерживаемые напрямую, эмулируются через пересоздание
- **Stack<T>**: Аналогично Queue, некоторые операции требуют пересоздания
- **ImmutableList<T>**: Каждая операция создает новую коллекцию, сохраняя неизменность исходной

## Результаты замеров

Результаты получены на коллекциях размером **100 000 элементов**. Каждая операция выполнялась **5 раз**, результаты усреднены. Время измеряется в **тиках процессора** (1 тик ≈ 100 наносекунд на современных процессорах).

### Анализ результатов

**Ключевые выводы:**

1. **Добавление в конец**: LinkedList (0.20 тиков) и Stack (0.20 тиков) показывают наилучшие результаты. List (7.00 тиков) медленнее из-за возможного перераспределения памяти.

2. **Добавление в начало**: LinkedList (2.80 тиков) значительно быстрее всех. List (105.60 тиков) требует сдвига всех элементов - O(n).

3. **Добавление в середину**: List (54.40 тиков) быстрее благодаря кэш-локальности. LinkedList (4,137.80 тиков) медленнее из-за необходимости поиска позиции.

4. **Удаление из начала**: Queue (0.20 тиков) и LinkedList (0.60 тиков). List (64.40 тиков) требует сдвига элементов.

5. **Удаление из конца**: Все коллекции показывают отличные результаты (< 1 тика).

6. **Поиск по значению**: List (72.60 тиков) и Stack (72.80 тиков) быстрее благодаря кэш-локальности. LinkedList (1,532.40 тиков) медленнее из-за промахов кэша.

7. **Доступ по индексу**: List (0.60 тиков). ImmutableList (1.20 тиков), но все еще очень быстро.

## Тестирование

Проект включает автоматизированные тесты для всех коллекций, проверяющие:

- Корректность добавления элементов
- Корректность удаления элементов
- Корректность поиска элементов
- Корректность доступа по индексу (где применимо)
- Сохранение порядка элементов
- Обработку граничных случаев

Все тесты детерминированы и воспроизводимы.
